In one picture

Four layers, dependencies only go down

Think of a console: the engine is the console, plugins are the cables to the screen, speakers and network, the game module is the cartridge, and the content is the levels on it.

4ContentYAML scenes and prefabs, scripts, sprites, sounds. Changed without recompiling.game designers
3Game moduleR-Type rules: Bydos, the Force, waves, score. Knows the engine, never SFML.gameplay devs
2Engine coreLoop, ECS, TypeRegistry, InputMap, EventBus, scenes, assets, plugin loader, services.engine devs
1Pluginsplatform (SFML or raylib), audio, network, scripting. Implement interfaces the core defines.engine devs

A layer knows its own interfaces and the ones below it, never the ones above. The engine does not know R-Type, R-Type does not know SFML, content only knows the names the game and engine expose. CMake enforces it: a forbidden include breaks the build.

One frame

The game loop

The same loop runs in the client and in the server room. The server skips the render step. Locked as E-04.

1 · Poll

Read the world outside

Platform plugin turns keyboard and gamepad into raw events, InputMap turns them into actions. Network packets become events.

2 · Fixed update ×N

Simulate in 1/60 s slices

Movement, collisions, AI. Always the same dt, so every machine and the server compute the same thing.

3 · Late update

Clean up

Deferred entity destruction, event dispatch, network send.

4 · Render (α)

Describe the frame

Render system fills the DrawCmd list, positions interpolated between the last two steps.

5 · Submit

Hand off once

One submit() into the platform plugin, which sorts by layer, batches by texture, draws.

accumulator += clock.restart();
poll();                                         // 1
while (accumulator >= STEP) {                   // 2: fixed, identical on every machine
    scheduler.run(Stage::FixedUpdate, STEP);
    accumulator -= STEP;
}
scheduler.run(Stage::LateUpdate);               // 3
scheduler.run(Stage::Render, accumulator / STEP); // 4: alpha in [0, 1)
platform.renderer().submit(renderQueue);        // 5: client only

Study · how real engines do it

Four separate questions behind "game as a module"

A. Who owns the loop. B. Who owns main(). C. How game code attaches to the engine. D. How the engine learns the game's types (reflection).

  • A is unanimous: every engine owns the loop. That is what separates an engine from a framework.
  • B is cosmetic: Bevy lets the game write main() and loses nothing. What matters is that the game never writes the loop.
  • C is the real decision, driven by four forces: modding and safety (VM, script), performance and consoles (static), iteration and editor (dynamic), many games on one engine (dynamic or data).
  • Unreal does not choose: it designs modules once and decides static or dynamic at build time.
  • Almost all have three layers: engine, game logic, and content for people who do not write C++.
  • D is unavoidable once you have scene files or an editor. In C++ without codegen, it is explicit registration: our TypeRegistry.
Under the hood

What a plugin really is

A .so / .dll the program opens when it decides, in which it looks up one function by a known name, which returns an object implementing an interface the engine knows.

KindLinuxWindowsWhen the code is attached
Static library.a.libAt build time. Copied into the executable.
Shared library, linked.so.dllAt startup. The OS loads it before main(); missing file, the program refuses to start.
Shared library, loaded on demand.so.dllAt runtime, when the program decides. This is a plugin.

The four mechanisms

  • Loading: dlopen / LoadLibrary opens the file, dlsym / GetProcAddress finds a function by name.
  • extern "C": C++ mangles names (_Z13create_pluginv), differently per compiler. extern "C" keeps create_plugin findable. Windows also needs __declspec(dllexport).
  • Interfaces and vtables: a virtual call jumps through a table of addresses filled by the plugin. The engine knows the shape of the contract, never the code.
  • ABI: the binary contract (object sizes, vtable layout, std::string layout). Different compilers or options break it silently, hence one toolchain, a version check, and "destroyed by its creator".
// engine side
DynamicLibrary lib("plugins/platform_sfml");   // .so or .dll
auto create = lib.symbol<IPlugin*(*)()>("create_plugin");
IPlugin* p = create();
if (p->apiVersion() != ENGINE_PLUGIN_API_VERSION)
    return Error("platform_sfml: API mismatch");

// plugin side
extern "C" EXPORT IPlugin* create_plugin()  { return new SfmlPlatform(); }
extern "C" EXPORT void destroy_plugin(IPlugin* p) { delete p; }

Decision ledger

Every engine decision so far

E-01Engine identityHybrid. A code-first ECS core like Bevy, with a Unity-like data layer later: YAML scenes and prefabs, inspector, editor. Components hold data only, never logic.Locked

Network part (2026-10-14)
N-1Who optimisesThe engine gives the means, the game team optimises. The engine is used without its code: it owns the bytes and exposes settings (budget, priority, relevance, quantisation) and extension points; prediction belongs to the game; engine interpolation is a default that can be turned off. ADR 0041.Locked
N-2AdmissionThe engine refuses only what it cannot decode (protocol version, game, types). The game accepts or refuses a player with its own reason, like Unreal's PreLogin or Unity's connection approval. ADR 0042.Locked
N-3Protocol MSEP v1.0Big-endian, magic "RT" + version, 16-byte UDP header with a session key and packet acks, TCP frames up to 64 KB, no fragmentation, replication sent until acknowledged, reconnection within 30 s with a single-use token, room transitions on the reliable UDP stream. 36 decisions (D1–D36), 40 scenarios. ADR 0043.Locked
Server part

One server, several games

Players who are not in a game are in the lobby; players who play together form a party; each game is a room. The engine moves parties between the lobby and rooms; the game decides when.

r-type_server (one process, Part 1)
 ├── Lobby          main thread, lobby code of the game
 │    ├── Party 1: Ola (leader), Michel
 │    └── Party 2: Sedjro        a party of 1
 ├── Room 7         Party 1: own world, events, tick
 └── Room 8         Party 2
      rooms run on a thread pool, one thread at a time per room

Where code runs

  • Game systems run in every room, with that room's Context.
  • Lobby code runs once on the main thread, with a LobbyContext (no world).
  • Client code asks through ClientLobby and changes scene on EnteredRoom.
  • Lobby and rooms talk only through messages, so one process per room stays possible in Part 2.
Network part

MSEP v1.0 at a glance

The protocol the engine speaks for every game. Everything in a running game travels on UDP; TCP carries only the connection and the lobby. Full specification: docs/network/rfc.md.

Budgets it is designed for

  • ≤ 64 KB/s down and ≤ 8 KB/s up per player, worst case; 32 players per server.
  • Playable at 150 ms round trip and 5 % loss; never broken at 20 %.
  • The subject's 5 KB/s test link: reached with the game's settings (budget, priority, 16-bit positions).
  • Measured by tasks SRV-20 (netem), fuzzed by SRV-18, visible in Wireshark with SRV-19.
Guard rails

Rules that come with dynamic modules

Plugin rules (E-02)

  • One CMake SHARED target per plugin, built into plugins/.
  • extern "C" create and destroy functions. Memory is freed by the module that allocated it.
  • An API version is checked at load. A mismatch gives a clear error, never a crash.
  • No exception crosses a module boundary.
  • One compiler and one C++ runtime for everything.
  • OS-specific loading code lives in one DynamicLibrary class.

Cross-module rules (E-06)

  • Component IDs come from the engine TypeRegistry, never from a static counter inside a template. Each .so would get its own counter.
  • Never use typeid or std::type_index as a key across modules.
  • No global singletons. Services such as the logger are passed into each module.
  • No SFML or raylib type ever appears outside its plugin. The core uses handles and its own Key, Color, Rect and Vec2.
