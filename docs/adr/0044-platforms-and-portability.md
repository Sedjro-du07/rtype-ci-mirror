# ADR 0044: Platforms and portability: Linux and Windows built, mobile designed for

- Status: Accepted
- Date: 2026-10-15
- Deciders: the R-Type team (choices delegated to the architect's recommendations)
- Discussion id: P-1 (multiplatform)

## Context

The subject requires Linux and Windows, and a Windows client playing on a Linux server. Pieces were
decided along the way (compilers, C++23 allow-list, plugin rules, `/MD`, big-endian protocol) but not
the whole: how `libengine` exports its API on Windows, where operating-system code lives, the portable
coding rules, and what else to keep possible. The team also asked to think about mobile.

## Decision

1. **Targets.** Built and tested in Part 1: Linux x64 (GCC 14+, Clang 18+) and Windows x64 (MSVC
   17.10+, Visual Studio 2022). macOS: best effort, not in CI. Android and iOS: not built in Part 1,
   designed for (point 6).
2. **One engine, shared.** In dynamic mode `libengine` is a shared library (`libengine.so`,
   `engine.dll`): the executable, every plugin and the game use one copy of the engine's state. In
   static mode it is a static library linked into one executable.
3. **Exports.** The public API is marked `ENGINE_API`, generated by CMake (`generate_export_header`,
   file `engine/Export.hpp` in the build tree): `dllexport` while building the engine, `dllimport` for
   its users, `visibility("default")` on Linux, empty in static mode. Every library builds with hidden
   visibility by default (`-fvisibility=hidden`, the MSVC default), so Linux behaves like Windows and
   a missing export fails on both. Templates and inline code stay in headers and need no mark.
   Plugins and games export only their entry points (`ENGINE_EXPORT`, unchanged).
4. **Operating-system layer.** `#ifdef _WIN32` and system headers are allowed only in
   `engine/src/os/` (new, private), in `DynamicLibrary` and in plugins. `os/` provides: secure random
   bytes (`getrandom` / `BCryptGenRandom`, for MSEP tokens), the user data folder
   (`$XDG_DATA_HOME` / `%APPDATA%`), the executable's folder, and quit signals (SIGINT, SIGTERM /
   console control handler) for the launcher.
5. **Portable code rules.** Paths are `std::filesystem::path`; files and strings are UTF-8 (MSVC
   `/utf-8`); asset paths are relative to the game root, use `/`, and must match the file's case
   exactly, checked on Windows too; fixed-width integers for anything written to disk or the wire;
   MSVC in conformance mode (`/permissive- /Zc:__cplusplus /Zc:preprocessor /EHsc`); `NOMINMAX` and
   `WIN32_LEAN_AND_MEAN` inside `os/` and plugins only; text files stored with LF
   (`.gitattributes`); no compiler extensions.
6. **Mobile, designed for.** Nothing mobile is built in Part 1, but nothing may block it:
   - **Static mode is the mobile build.** iOS forbids loading app code at runtime; Android allows it
     but static is simpler. CI builds static mode on every commit so it never rots.
   - **Platform.** `platform_raylib` (Part 2) runs on Android; SFML 3 has experimental mobile support.
     A mobile port is a platform plugin, not an engine change.
   - **Touch.** `RawInputEvent` reserves `TouchDown`, `TouchUp`, `TouchMove` (finger id, position in
     virtual resolution). Desktop plugins never send them; binding touch zones to actions comes with a
     mobile port.
   - **Lifecycle.** Engine events `AppSuspended` and `AppResumed` are reserved; desktop plugins never
     send them. A suspended client loses its connection and comes back through MSEP reconnection
     (grace period, UDP relink after a network change, D16–D17).
   - **Files.** The game root may be read-only or packed (Android APK): the engine never writes under
     it. Settings, logs and captures go to the user data folder (point 4).
   - **Screens.** Virtual resolution, letterboxing and UI scale already adapt to any screen.

## Alternatives considered

- **`CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS`:** exports functions automatically but not static data, and
  hides the API surface; explicit `ENGINE_API` documents what games may use.
- **Static `libengine` linked into each plugin:** every plugin would get its own TypeRegistry, logger
  and registries; breaks the shared state the design relies on.
- **macOS or mobile builds in Part 1:** extra CI and platform work the subject does not ask for.

## Consequences

- ENG-01 sets the export header, visibility and compiler options; new task ENG-60 writes `src/os/`.
- ENG-27 and ENG-28 declare the reserved mobile events; ENG-40 checks path case; ENG-45 saves settings
  in the user data folder.
- A Linux build that forgot an `ENGINE_API` fails like Windows would, so the error is seen early.
